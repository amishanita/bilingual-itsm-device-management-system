# 運用手順書

ITSM端末管理システムの日常運用（バックアップ、リストア、再起動、ユーザー追加、アップデート）の手順です。
サーバーの構築方法は [構築手順書](構築手順書.md)、トラブル時の対応は [障害対応手順書](障害対応手順書.md) を参照してください。

> 本書のコマンドは、サーバーに `ubuntu` ユーザーでSSH接続し、`~/itsm-platform` で実行することを前提にしています。
> データベース名とユーザー名は `.env.example` の初期値（`itsm`）とします。

毎回入力が長くなるため、作業前に次のエイリアスを設定しておくと便利です。

```bash
cd ~/itsm-platform
alias dc='docker compose -f docker-compose.prod.yml'
```

## 1. 定期確認

| 頻度 | 確認内容 | 方法 |
| --- | --- | --- |
| 毎朝 | バックアップが成功しているか | `tail -n 3 ~/itsm-logs/backup.log`（最終行が `backup complete`） |
| 毎週月曜 | 日曜のリストア確認が成功しているか | `tail -n 3 ~/itsm-logs/restore-check.log`（`restore check passed`） |
| 毎週 | ディスク使用率 | `df -h /`（80%を超えたら [障害対応手順書](障害対応手順書.md) の「2」を参照） |
| 毎月 | AWSの請求額 | 請求コンソール。予算を超えそうな場合はメールが届きます |
| 毎月 | 自分のIPが変わっていないか（SSH） | SSHできなくなった場合は「6. SSHの接続元IPの変更」 |

## 2. バックアップ

毎日03:00に自動で実行されます。内容は次のとおりです。

1. `pg_dump` でデータベース全体を出力し、gzipで圧縮
2. 出力が途中で切れていないことを確認
3. S3へ暗号化（AES256）して保存し、保存後のサイズが一致することを確認
4. サーバー上の一時ファイルを削除

保存先：`s3://<BACKUP_S3_BUCKET>/itsm/<年>/<月>/itsm-<日時>.sql.gz`（30日経過で自動削除）

**手動で実行する場合**（アップデート前など）：

```bash
scripts/backup.sh
```

**保存されているバックアップの一覧：**

```bash
aws s3 ls s3://<BACKUP_S3_BUCKET>/itsm/ --recursive | tail -n 10
```

## 3. リストア

### 3-1. まず検証（本番データには影響なし）

戻したいバックアップが正常かどうかを、別のデータベース（`itsm_restore_check`）に復元して確認します。

```bash
scripts/restore-check.sh                                  # 最新のバックアップ
scripts/restore-check.sh itsm/2026/10/itsm-20261017T180000Z.sql.gz   # 指定したバックアップ
```

`restore check passed` と、ユーザー数・端末数などの件数が表示されることを確認します。

### 3-2. 本番データベースへの復元

**本番データを上書きします。** 実施前に関係者へ連絡し、メンテナンス時間を確保してください。
復元時点以降に登録されたデータは失われます。

```bash
# 1) 念のため、現在の状態をバックアップ
scripts/backup.sh

# 2) 戻すバックアップをダウンロード（キーは「2. バックアップ」の一覧で確認）
KEY=itsm/2026/10/itsm-20261017T180000Z.sql.gz
aws s3 cp "s3://<BACKUP_S3_BUCKET>/$KEY" /tmp/restore.sql.gz
gzip -t /tmp/restore.sql.gz && gzip -dc /tmp/restore.sql.gz | tail -n 5 | grep "dump complete"

# 3) APIを停止（画面は「接続できません」の表示になります）
dc stop api

# 4) データベースを作り直して復元
dc exec -T db psql -U itsm -d postgres -c "DROP DATABASE itsm WITH (FORCE)"
dc exec -T db psql -U itsm -d postgres -c "CREATE DATABASE itsm"
gzip -dc /tmp/restore.sql.gz | dc exec -T db psql -q -v ON_ERROR_STOP=1 -U itsm -d itsm > /dev/null

# 5) APIを起動して確認
dc start api
dc ps
curl -s https://<SITE_DOMAIN>/api/health

# 6) 一時ファイルを削除
rm -f /tmp/restore.sql.gz
```

- 手順2で `PostgreSQL database dump complete` が表示されない場合は、ファイルが壊れているか途中で切れています。
  **データベースを削除する前に中止し**、別のバックアップを使ってください。途中で切れたファイルは、
  エラーにならずに一部のデータだけが復元されることがあるため、この確認は省略しないでください。
- 手順4でSQLエラーが出た場合は処理が止まります。APIは起動せず、手順1で取得した直前のバックアップを同じ手順で復元してください。

## 4. 再起動

| 状況 | コマンド |
| --- | --- |
| 状態の確認 | `dc ps` |
| APIのみ再起動（`.env` を変更した後など） | `dc up -d api` |
| すべて再起動 | `dc restart` |
| 停止 | `dc stop` |
| 起動 | `dc up -d` |
| サーバー自体の再起動 | `sudo reboot`（コンテナは `restart: unless-stopped` により自動で起動します） |

`.env` の変更は `dc restart` では反映されません。`dc up -d api` でコンテナを作り直してください。

**ログの確認：**

```bash
dc logs --tail 100 api        # API
dc logs --tail 100 caddy      # Webサーバー（HTTPS、アクセスログ）
dc logs --tail 100 db         # データベース
```

コンテナのログは1つにつき最大10 MB × 3ファイルで自動的にローテーションされます。

## 5. ユーザーの追加・変更

ログインアカウントの管理は super_admin のみが行えます。

1. 対象者の社員情報がなければ、「社員」画面で先に登録します（IT担当者または super_admin）。
2. super_admin でサインインし、メニューの「ユーザー管理」を開きます。
3. 「ユーザーを作成」から、メールアドレス、初期パスワード（8文字以上）、ロール、紐付ける社員を入力します。
4. 初期パスワードは本人に安全な方法で伝えます（チャットに平文で残さない）。

| 操作 | 方法 |
| --- | --- |
| ロールの変更 | 「ユーザー管理」画面で対象者を編集 |
| 利用停止 | 「ユーザー管理」画面で無効にする（次のリクエストから利用できなくなります） |
| 退職者 | 「社員」画面で退職済みにすると、紐付いたログインも無効になります。保有端末は1台ずつ返却処理をしてください |
| パスワードのリセット | 「ユーザー管理」画面で新しいパスワードを設定 |

注意：
- 有効な super_admin が1人しかいない場合、その人のロール変更や無効化はできません。
- `APP_ENV=demo` では4つのデモアカウントは変更できません。また、毎晩03:30にデータが初期状態に戻るため、
  追加したユーザーも削除されます。

## 6. SSHの接続元IPの変更

自宅などのIPアドレスが変わるとSSHで接続できなくなります。作業用PCで次を実行します。

```bash
curl -s https://checkip.amazonaws.com
cd infra/terraform
# terraform.tfvars の my_ip を新しいIP/32 に変更
terraform plan      # ファイアウォールの変更のみであることを確認
terraform apply
```

## 7. アプリケーションのアップデート

```bash
cd ~/itsm-platform

# 1) 更新前のバックアップ
scripts/backup.sh

# 2) 取得する変更の確認
git fetch
git log --oneline HEAD..origin/main

# 3) 更新
git pull --ff-only
dc up -d --build
dc exec api alembic upgrade head

# 4) 確認
dc ps
curl -s https://<SITE_DOMAIN>/api/health
```

- 画面（`frontend/`）は `git pull` の時点で反映されます。ブラウザは毎回更新を確認する設定のため、キャッシュ削除は不要です。
- `.env.example` に新しい項目が追加されていないか確認し、必要なら `.env` にも追加してください（`git diff HEAD@{1} -- .env.example`）。
- 不具合が出た場合は、`git log` で直前のコミットを確認して `git checkout <コミット>` で戻し、`dc up -d --build` を実行します。
  マイグレーションでテーブル構成が変わった場合は、「3. リストア」で更新前のバックアップに戻してください。

**OSの更新：** セキュリティ更新は自動で適用されます。カーネル更新後は再起動が必要な場合があります。

```bash
cat /var/run/reboot-required 2>/dev/null && echo "再起動が必要です"
```

## 8. チャットボットの有効化・停止

| 操作 | 方法 |
| --- | --- |
| 有効化 | `.env` の `OPENAI_API_KEY` と `OPENAI_MODEL`（ツール呼び出し対応モデル）を設定し、`dc up -d api`。新しいモデルでは `OPENAI_REASONING_EFFORT=none` も必要です |
| 停止 | 上記2項目を空欄にして `dc up -d api`（チャット画面には「現在チャットは利用できません。問い合わせフォームからご連絡ください。」と表示されます） |

有効化する場合は、OpenAI側で月の利用上限を必ず設定してください。利用はユーザーごとに1時間20回までに制限しています。
