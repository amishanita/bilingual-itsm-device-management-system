# 障害対応手順書

ITSM端末管理システムで障害が発生した場合の切り分けと対応手順です。

> 本書のコマンドは、サーバーに `ubuntu` ユーザーでSSH接続し、`~/itsm-platform` で次のエイリアスを設定した状態で実行します。
>
> ```bash
> cd ~/itsm-platform
> alias dc='docker compose -f docker-compose.prod.yml'
> ```

## 0. 共通の初動

1. **影響範囲を確認する**：全員が使えないのか、特定の画面・特定のユーザーだけか。
2. **発生時刻と直前の作業を確認する**：アップデート、`.env` の変更、AWS側の操作などがなかったか。
3. **データを守る**：原因が分かるまで、データベースのボリューム（`pgdata`）や証明書のボリューム（`caddy_data`）は削除しない。
   `docker compose down -v` や `docker volume rm` は実行しないでください。
4. **記録を残す**：実行したコマンドと結果、時刻を控え、復旧後に報告します。

| 症状 | 参照 |
| --- | --- |
| サイトが開かない、「接続できません」 | 1 |
| 保存できない、データベースのエラー、ディスク不足 | 2 |
| ブラウザに証明書の警告が出る | 3 |
| チャットボットが応答しない | 4 |
| SSHで接続できない | 5 |

## 1. サイトに接続できない

### 1-1. 外部から状態を確認（作業用PC）

```bash
curl -sS -o /dev/null -w "%{http_code}\n" https://<SITE_DOMAIN>/
curl -sS https://<SITE_DOMAIN>/api/health
```

| 結果 | 考えられる原因 | 次の確認 |
| --- | --- | --- |
| 接続タイムアウト、名前解決できない | サーバー停止、IPの変更、ファイアウォール | 1-2 |
| 画面は200だが `/api/health` が502 | APIコンテナが停止・異常 | 1-3 |
| `/api/health` が503で `DATABASE_UNAVAILABLE` | データベースの停止、ディスク不足 | 2 |
| 証明書エラー | 証明書の取得・更新失敗 | 3 |

### 1-2. サーバー自体の確認

1. Lightsailコンソールでインスタンス `itsm-app` が「実行中」か確認します。停止していれば起動します。
2. 静的IP `itsm-ip` がインスタンスにアタッチされているか確認します。
3. 「ネットワーク」タブで、80・443が全体に開いているか確認します（変更されていれば `terraform apply` で元に戻ります）。
4. SSHで接続できる場合は、リソースを確認します。

```bash
uptime
free -m
df -h /
```

### 1-3. コンテナの確認

```bash
dc ps
```

| 状態 | 対応 |
| --- | --- |
| すべて `Up`、`healthy` | Caddyのログを確認（`dc logs --tail 100 caddy`） |
| `api` が `unhealthy` または再起動を繰り返す | `dc logs --tail 100 api` で起動時のエラーを確認（下表） |
| `db` が停止 | `dc logs --tail 100 db`。ディスク不足なら「2」へ |
| 何も表示されない | `dc up -d` で起動 |

APIの起動時によくあるエラー：

| ログの内容 | 原因と対応 |
| --- | --- |
| `JWT_SECRET` に関するエラー | `.env` の `JWT_SECRET` が空、短い、または例の値のまま。32文字以上の値を設定し `dc up -d api` |
| `could not translate host name "db"` / `connection refused` | データベースが起動していない。`dc up -d db` の後、`dc up -d api` |
| `password authentication failed` | `.env` の `POSTGRES_PASSWORD` を変更した。DBのパスワードは初回作成時の値のまま変わらないため、元の値に戻す |
| `ModuleNotFoundError` など | アップデート後のビルド漏れ。`dc up -d --build` |

### 1-4. 再起動で復旧を試みる

原因が分からない場合は、データを消さない範囲で順に試します。

```bash
dc restart api
dc restart
sudo reboot
```

再起動後、`curl -sS https://<SITE_DOMAIN>/api/health` で確認します。

## 2. データベースの容量不足・ディスク不足

### 2-1. 確認

```bash
df -h /
docker system df
dc exec db psql -U itsm -d itsm -c "SELECT pg_size_pretty(pg_database_size('itsm'))"
```

Lightsailの1 GBプランのディスクは40 GBです。このシステムのデータベースは通常数十MB程度のため、
ディスク不足の原因の多くは、古いDockerイメージ、ビルドキャッシュ、ログです。

### 2-2. 空き容量の確保（データベースには影響なし）

```bash
docker image prune -f              # 使われていない古いイメージ
docker builder prune -f            # ビルドキャッシュ
sudo journalctl --vacuum-time=7d   # 7日より古いシステムログ
ls -lh ~/itsm-logs/                # cronのログ（大きければ古い行を削除）
```

コンテナのログは1つあたり最大30 MBで自動的にローテーションされるため、通常は原因になりません。
`/tmp` にリストア作業のファイル（`restore.sql.gz` など）が残っていれば削除します。

### 2-3. データベースの復旧

ディスクが一杯になるとPostgreSQLは書き込みを止めて停止することがあります。空き容量を確保した後に起動します。

```bash
dc up -d db
dc logs --tail 50 db
dc up -d api
curl -sS https://<SITE_DOMAIN>/api/health
```

ログに `database system was not properly shut down` と出ても、続けて `database system is ready to accept connections`
と出ていれば自動で復旧しています。データの破損が疑われる場合は [運用手順書](運用手順書.md) の「3. リストア」で、
直近のバックアップから復元します。

### 2-4. 再発防止

- `df -h` の確認を週次の定期確認に入れる（[運用手順書](運用手順書.md) の「1」）。
- データ量が増え続ける場合は、Lightsailのブロックストレージ追加または上位プランへの変更を検討する。

## 3. 証明書エラー

HTTPS証明書はCaddyがLet's Encryptから自動で取得・更新します（有効期限90日、期限の約30日前に自動更新）。

### 3-1. 確認

```bash
dc logs --tail 200 caddy | grep -iE "certificate|acme|tls|error"
echo | openssl s_client -connect <SITE_DOMAIN>:443 -servername <SITE_DOMAIN> 2>/dev/null | openssl x509 -noout -dates -issuer
```

### 3-2. 原因と対応

| 状況 | 原因 | 対応 |
| --- | --- | --- |
| 初回から証明書が取れない | `SITE_DOMAIN` がサーバーのIPを指していない | `dig +short <SITE_DOMAIN>` の結果が静的IPと一致するか確認。sslip.io の場合はIPの `.` を `-` にした形式か確認 |
| 同上 | 80・443が閉じている | Let's Encryptの確認には外部からの80/443接続が必要。Lightsailのファイアウォールを確認（「1-2」の3） |
| ログに `too many certificates` / `rateLimited` | Let's Encryptの発行回数制限 | 時間をおいて再試行。**`caddy_data` ボリュームを削除して再取得を繰り返さないこと**（制限に達しやすくなります） |
| 有効期限切れ | 自動更新の失敗 | 上記の原因を解消後、`dc restart caddy` |
| 証明書の日付が合わない | サーバーの時刻ずれ | `timedatectl` で `System clock synchronized: yes` を確認 |
| 独自ドメインに変更した | `.env` の変更が未反映 | `.env` の `SITE_DOMAIN` を変更後、`dc up -d caddy api` |

`SITE_DOMAIN` を変更した場合は、APIの許可オリジン（`FRONTEND_ORIGIN`）も自動で変わるため、`api` も作り直してください。

## 4. チャットボットが応答しない

### 4-1. 画面の表示から切り分け

| チャット画面の表示 | 原因 | 対応 |
| --- | --- | --- |
| 「現在チャットは利用できません。問い合わせフォームからご連絡ください。」 | `OPENAI_API_KEY` または `OPENAI_MODEL` が未設定（意図的に停止している状態） | 有効にする場合は [運用手順書](運用手順書.md) の「8」 |
| 「チャットサービスが応答していません。しばらくしてから再度お試しください。」 | 外部API（OpenAI）のエラー | 4-2でログを確認 |
| 「試行回数が多すぎます。…」 | 1ユーザーあたり1時間20回の上限 | 時間をおいて再度利用。仕様どおりの動作です |
| 「登録する」を押すと確定期限切れのエラー | 問い合わせ案の確定期限（10分）切れ | もう一度チャットで依頼する |

### 4-2. ログの確認

```bash
dc logs --tail 200 api | grep "Chat provider error"
```

ログには、秘密情報を残さないためエラーの種類だけが出力されます。

| エラーの種類 | 原因 | 対応 |
| --- | --- | --- |
| `AuthenticationError` | APIキーが無効・失効 | OpenAIで新しいキーを発行し、`.env` を更新して `dc up -d api` |
| `RateLimitError` | OpenAI側の回数制限、または利用上限・残高不足 | OpenAIの管理画面で利用状況と上限を確認 |
| `NotFoundError` | `OPENAI_MODEL` のモデル名の誤り | 正しいモデル名に修正 |
| `BadRequestError`（`param=reasoning_effort`） | 新しいモデルでは、推論設定のままツール呼び出しを使えない | `.env` に `OPENAI_REASONING_EFFORT=none` を設定し、`dc up -d api` |
| `BadRequestError`（その他の `param`） | ツール呼び出しに対応していないモデル、または未対応の設定 | `param` に表示された項目を確認し、対応モデルに変更 |
| `APITimeoutError` / `APIConnectionError` | 応答の遅延、通信障害 | OpenAIの障害情報を確認。必要に応じて `OPENAI_TIMEOUT_SECONDS` を延長 |

チャットボットが使えない間も、問い合わせフォームからのチケット登録は通常どおり利用できます。
利用者にはフォームの利用を案内してください。

## 5. SSHで接続できない

| 原因 | 対応 |
| --- | --- |
| 自宅などのIPアドレスが変わった | [運用手順書](運用手順書.md) の「6」で `my_ip` を更新 |
| サーバーが停止している | Lightsailコンソールで起動 |
| 鍵が違う | `ssh -i ~/.ssh/id_ed25519 ubuntu@<static_ip>` のように鍵を明示 |

どうしても接続できない場合は、Lightsailコンソールの「ブラウザを使用して接続」も利用できますが、
ファイアウォールでポート22を一時的に開く必要があるため、作業後は必ず `terraform apply` で元に戻してください。

## 6. 復旧後の報告

復旧後、次の項目を記録して関係者に共有します。

- 発生日時・検知方法
- 影響範囲（利用できなかった機能、時間）
- 原因
- 実施した対応（コマンドと結果）
- データ損失の有無（リストアした場合は、どの時点に戻したか）
- 再発防止策
